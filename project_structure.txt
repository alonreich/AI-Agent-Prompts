The project is designed for maximum portability and zero-clutter. The root
directory contains only 8 permanent files.

ROOT/

├── Install.bat             # Master Setup, Dependency Installer & Health Verifier
├── UnInstall.bat           # Removes persistence, processes, and logs

├── README.md               # Public-facing project overview
├── project_structure.txt   # This Manual (Architectural Source of Truth)

└── bridge.py               # Sequence-Aware Flask Backend

All data is isolated within two root-level directories:
├── AI Agent Prompts/       # Physical Persistence Layer
└── [RECYCLE BIN]/          # Soft Deletion Archive

2. PHYSICAL DATA PERSISTENCE (SEQUENTIAL SCHEMA)
===============================================================================
Groups are stored as physical directories using a strict sequential pattern. 
This sequence is the "Source of Truth" for the UI order.

Schema: "GroupX - [Title]"
Example:
├── Group1 - [GENERAL]
├── Group2 - [BUG DETECTOR]
└── Group3 - [Fortnite]

RULES:
- [GENERAL] Priority: The "GENERAL" title is hard-locked to always be Group 1.
- Gapless Sequence: The backend automatically re-indexes all folders (1, 2, 3...) 
  whenever a group is created, moved, or deleted. There are never gaps.
- Character Safety: Forbidden Windows characters (< > : " / \ | ? *) are 
  automatically replaced with underscores (_) to prevent Error 123.

3. AUTOMATED LIFECYCLE MANAGEMENT
===============================================================================
The system operates autonomously with zero manual maintenance required.

A. Persistent Scaffolding:
   - Group folders are preserved even when empty to maintain organizational 
     structure and user metadata.
   - Deletion of groups is an explicit, user-initiated action via the UI.
   - Triggered by: Moving the last agent out, or direct file deletion.

B. Atomic "Mirror Sync":
   - Uses a high-speed Watchdog observer to monitor the disk.
   - Any change made directly to folders/files is reflected in the UI within 
     0.5 seconds (bidirectional sync).

C. Reorder Safety (/api/save-order)
   Renaming folders into a new sequence is inherently destructive. Four rules,
   all of them written after a reorder made three groups disappear:
   1. The request must list EVERY group. The old code renamed only the folders
      it was given and DELETED whatever occupied a destination, so a partial
      order - which the UI produced whenever a search filter was active - could
      permanently destroy a group it was merely hiding. Partial orders are now
      rejected with 400 and the frontend refuses to send one at all
      (group drag is blocked while the board is filtered).
   2. Temp folder names embed the ORIGINAL folder name
      (.tmp_re_<ts>_<i>__Group3 - [FORTNITE]), so a crash between the two
      rename passes is always recoverable. The old name (.tmp_re_<i>_<ts>)
      threw the title away and made recovery guesswork.
   3. NOTHING is ever deleted to make room. An occupied destination aborts the
      operation. This applies to migrate_folders_locked() too.
   3b. A group whose name is ALREADY correct is never touched. Renaming it out
      to a temp and straight back achieved nothing and was a pure opportunity
      for Windows to deny the rename - which it did, failing whole reorders in
      which that group was not even moving.
   3c. Every rename goes through robust_rename(), which retries with backoff.
      Windows returns WinError 5 (access denied) on a directory rename while
      anything holds a handle inside it: an antivirus scanning the folder that
      was just touched, the search indexer, or an Explorer window sitting on it.
      The lock is almost always transient. Same reasoning as robust_rmtree.
   4. Any failure rolls every folder back to the name it started with, in two
      passes (one group's original name can be another group's new name).

D. Orphan Recovery (adopt_orphan_group_folders)
   Runs at the top of migrate_folders_locked(), i.e. on every data read, so a
   group stranded by an interrupted rename reappears within half a second
   instead of being invisible until someone digs through the folder on disk.
   Understands all three temp naming formats; a legacy temp with no recoverable
   title comes back as "[RECOVERED GROUP]" rather than staying hidden. Every
   recovery is logged at WARNING level.

E. Atomic Move Operations:
   - Drag-and-drop actions use a dedicated backend `/api/move` endpoint.
   - Relocations are performed as a single disk move (`shutil.move`), 
     eliminating duplicates and ensuring data integrity.

4. SYSTEM OPERATION & STARTUP
===============================================================================
- Network: Runs on http://127.0.0.1:5589 (loopback only — never exposed to LAN).
- Visibility: Operates invisibly via 'pythonw.exe' (full interpreter path is
  resolved at install time; startup never depends on the logon PATH).
- Single Instance: bridge.py probes /api/ping on startup and exits quietly if
  another bridge instance is already serving port 5589. Duplicate processes
  are therefore impossible regardless of how the bridge is launched.
- Persistence (primary): A Windows Scheduled Task named 'AIAgentPromptBridge'
  runs at user logon with STANDARD (non-admin) privileges.
- Persistence (fallback): If task creation fails, a VBS launcher is created at:
  %LOCALAPPDATA%\AIAgentPromptController\silent_start.vbs
  plus a shortcut in the user's Startup folder.
- Portability: NO install path is ever hardcoded. bridge.py derives its root
  from its own file location, and Install.bat derives paths from wherever it
  is run. At startup the installer asks the user to choose: run in place
  (wherever the user put the folder) or copy the project to the standard
  C:\AI-Agent-Prompt\ folder and install from there.
- Installer: 'Install.bat' probes before acting (Python via 'python' or the
  'py' launcher, importability of dependencies, bridge.py syntax check, and
  port 5589 ownership — it refuses to kill an unknown app on the port). After
  setup it launches the backend and VERIFIES health: it polls /api/ping for up
  to 20 seconds and confirms /api/data serves successfully, reporting loud,
  explicit errors (with log paths) if the backend fails to come online.
- Restart: 'Restart-Bridge.bat' restarts the bridge PROCESS without touching
  persistence. It self-elevates via UAC, resolves the task name (tries
  'AIAgentPromptBridge', then the legacy 'AIAgentBridge', then queries Task
  Scheduler for any task whose action references bridge.py), ends it, kills
  the PID from the PID file plus anything still listening on 5589 plus any
  stray python process holding bridge.py, waits for the port to clear, purges
  __pycache__, then re-runs the task via 'schtasks /run' so Task Scheduler
  keeps owning the process and the logon trigger is unchanged. Finally it
  polls /api/ping for up to 20s and reports the new PID and version.
  Falls back to the Startup-folder VBS launcher when no task exists.
  Use Install.bat only for a full (re)install.
- Security: The API only accepts browser requests originating from its own
  pages (http://127.0.0.1:5589, http://localhost:5589, or the HTML file opened
  from disk). Cross-site requests from foreign websites are rejected (403),
  protecting local data from drive-by CSRF attacks.

### 1. UI/UX & Accessibility Hardening
- Purpose: Ensure the application meets enterprise-grade usability, visual hierarchy, and WCAG accessibility standards.
- User goal: Interact with the application seamlessly without visual friction or accessibility barriers.
- Main behavior: Adjusts CSS variables and element states for enhanced usability feedback.
- UI/UX behavior:
  - Success/Warning backgrounds pass WCAG AA 4.5:1 contrast ratios.
  - Form inputs display a clear, accessible focus ring on interaction.
  - Disabled buttons show a `not-allowed` cursor on hover.
  - Drag handles show `cursor: grabbing` when active.
  - Modal buttons (`.wiz-save`, `.wiz-cancel`) have standard padding, transitions, and `cursor: pointer`.
- Logic Details: CSS variables updated `--success` changed to `#238636`, `--warning` changed to `#9e6a03`. `pointer-events: none` was removed from disabled buttons in favor of `cursor: not-allowed` and `opacity: 0.5`. `:active` pseudo-classes added to drag handles. Modal buttons were explicitly given `padding: 10px 24px`, `cursor: pointer`, and `transition: 0.2s`.
- Edge Cases: Focus rings must not clip outside modal boundaries. If other CSS rules override modal buttons, `.wiz-save` explicitly enforces padding and cursor.
- Acceptance Criteria: 
  1. System shows `not-allowed` cursor when hovering over disabled buttons.
  2. System renders a visible focus ring when form inputs are focused.
  3. System passes WCAG AA contrast ratio checks for success and warning elements.

### 2. Duplicate Python Process Prevention
- Purpose: Prevent background zombie processes and port collision issues caused by duplicate bridge instances.
- Main behavior: The installation script aggressively hunts and deletes outdated startup methods before creating the new scheduled task.
- System behavior: Deletes old `.lnk` files and old scheduled tasks before registering the new task.
- Permission rules: Script must be run as Administrator to modify Scheduled Tasks.
- Failure handling: If a shortcut doesn't exist, the deletion command fails silently without stopping the script (`>nul 2>&1`).
- Logic Details: Execute deletion commands targeting `%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup\AIAgentBridge.lnk` and `AIAgentPromptBridge.lnk`. Execute `schtasks /delete` for legacy task names before setting up the correct task.
- Edge Cases: If the files are already deleted, the script ignores the error and proceeds. If only some legacy files exist, only those are deleted.
- Acceptance Criteria:
  1. System deletes legacy `.lnk` files from the Startup folder.
  2. System does not spawn two identical python processes on boot.
  3. System safely ignores errors if legacy files are not found.

### 3. Strict Unsaved Changes Detection
- Purpose: Remove friction and annoyance when navigating away from unmodified prompts.
- Main behavior: Verifies string equality between the live text box and the stored dictionary data before firing the modal.
- System behavior: Silently calls `stopEdit()` and navigates if the strings match perfectly.
- Data rules: Live `innerText` is compared against `groups[currentGroup].agents[currentAgent]`.
- Failure handling: If the dictionary key is somehow missing, the comparison evaluates as changed to safely prevent data loss.
- Logic Details: Calculates a `hasRealChanges` boolean. It evaluates to `true` ONLY IF `box.classList.contains('editing')` AND `box.innerText !== groups[currentGroup].agents[currentAgent]`. If false, executes `stopEdit()` and routes immediately.
- Edge Cases: Invisible DOM formatting (like `contenteditable` injecting `<br>`) must not trigger false positives. The use of `innerText` against raw text string mitigates this.
- Acceptance Criteria:
  1. Feature shows a warning modal when the user modifies text and attempts to navigate away.
  2. Feature does not show a warning modal when the user enters edit mode but makes zero string changes.

### 4. Group-Locked Prompt Navigation
- Purpose: Keep the user focused on the contextual grouping they are currently reviewing.
- Main behavior: The navigation list array is restricted strictly to the bounds of the `currentGroup`.
- System behavior: Compiles an active list of agents only belonging to the currently active folder.
- UI/UX behavior: Arrows disable natively when `idx <= 0` or `idx >= list.length - 1`. Cross-group text hints are deprecated and hidden.
- Logic Details: Replaced `buildAllAgentsList()` with `buildGroupAgentsList()`, which iterates only over `Object.keys(groups[currentGroup].agents)`. Removed DOM manipulation associated with cross-hints.
- Edge Cases: Rapid clicking of the arrow prevents array out-of-bounds exceptions via a strict length check constraint.
- Acceptance Criteria:
  1. System disables the "Next" arrow when viewing the last prompt in the current group.
  2. System disables the "Previous" arrow when viewing the first prompt in the current group.
  3. Feature never loads a prompt belonging to a different group.

### 5. External AI Prompt Reviewer
- Purpose: Provide immediate, free, and robust AI feedback on prompt engineering quality without requiring API keys.
- Main behavior: Packages raw text into a strict template and opens ChatGPT with the payload pre-filled via URI parameters.
- System behavior: Executes `window.open` targeting `https://chatgpt.com/?q=...`.
- Data rules: Text payload is `encodeURIComponent()` sanitized.
- UI/UX behavior: An elliptical, purple button (`.ai-review-btn`) sits in the top right of the header, featuring a tooltip and star SVG. Hides natively when the user enters editing state.
- Failure handling: If the browser blocks popups, the user must manually allow it.
- Logic Details: The `reviewPromptWithAI()` function wraps `box.innerText` inside a strict prompt requesting bulleted summaries, hallucination guard checks, and simplified reprints.
- Edge Cases: Formatting/line breaks are safely preserved via URI encoding. Handled natively by ChatGPT's rate limits.
- Acceptance Criteria:
  1. Feature opens a new tab directed to ChatGPT when clicked.
  2. System securely passes the exact text of the active prompt inside the URL parameter.
  3. Button disappears correctly when the user enters edit mode.

### 6. Smart Flex-Wrap Dashboard Layout
- Purpose: Maximize horizontal screen real estate by allowing narrow groups to pack tightly next to wide groups.
- Main behavior: Groups dynamically scale to `fit-content` but remain bound by hard max/min constraints.
- System behavior: Groups wrap naturally using CSS Flexbox flowing left-to-right.
- UI/UX behavior: 
  - `#main-menu` uses `display: flex; flex-wrap: wrap;`.
  - `.group-container` uses `width: fit-content; min-width: 220px; max-width: 350px;`.
  - Group padding is strictly locked to `12px 30px 15px 30px`.
  - `.agent-card` uses `max-width: 100%` to fill their parent container and force text wrapping when parent caps at 350px.
  - `.group-grid` uses `flex-direction: column` to strictly stack internal cards downwards.
- Logic Details: CSS Grid `auto-fill` was completely removed in favor of `flex-wrap`. Internal card flow issue (cards sitting side-by-side) was mitigated by removing `flex-wrap: wrap` from the internal `.group-grid` and replacing it with `flex-direction: column; align-items: center`.
- Edge Cases: If a single uninterrupted word exceeds 350px, standard `overflow-wrap: anywhere` CSS kicks in. On mobile screens (`max-width: 768px`), flexbox naturally wraps to 1 item per row.
- Acceptance Criteria:
  1. System aligns groups left-to-right, wrapping to the next line when screen space runs out.
  2. System forces group containers to shrink horizontally to fit short text tightly.
  3. System prevents any group from growing wider than 350px.
  4. System stacks all agent cards in a strict vertical line, never rendering them side-by-side inside the same group.

### 7. Native Recycle Bin & Soft Deletion
- Purpose: Prevent catastrophic data loss when users delete prompts or entire groups, providing a 30-day recovery window.
- Main behavior: Items deleted via the UI or Drag-and-Drop are moved to a hidden `[RECYCLE BIN]` directory on the filesystem rather than being permanently destroyed.
- System behavior: 
  - Every deletion creates a timestamped folder inside `[RECYCLE BIN]` and writes a `.bin_meta.json` file containing the original group name, item name, type ('group' or 'agent'), and deletion timestamp.
  - A background cleanup function (`cleanup_recycle_bin()`) runs automatically when the Flask server starts, permanently purging items older than 30 days (`RECYCLE_RETENTION_DAYS = 30`).
- UI/UX behavior:
  - Users delete items by dragging them into the "Global Trash Zone" (bottom right, appears only during drag) or using inline trash icons.
  - A persistent "Recycle Bin" button with a dynamic notification badge tracks the count of deleted items.
  - Clicking the bin opens a modal to view, individually restore (`/api/recycle-restore`), individually purge (`/api/recycle-purge`), or "Empty Recycle Bin" (`/api/recycle-purge-all`).
- Data rules: Restoring an agent attempts to put it back in its original group. If the group no longer exists, it is placed in the `[GENERAL]` group.
- Failure handling: Safe cleanup utilizing `robust_rmtree()` to prevent permission locks on Windows.
- Edge Cases: Duplicate filenames in the recycle bin are handled by appending a numeric counter `ts_counter_safeName`.
- Acceptance Criteria:
  1. Deleted files are physically moved to `[RECYCLE BIN]` and not destroyed.
  2. Items older than 30 days are automatically deleted upon bridge startup.
  3. The recycle bin badge updates immediately after a deletion.

### 8. Drag and Drop Architecture (Groups & Agents)
- Purpose: Allow fluid reorganization of agents across groups, and reordering of the groups themselves.
- Main behavior: Client-side HTML5 drag-and-drop combined with atomic backend folder manipulation.
- System behavior: 
  - Agent Drag: Relocates the agent's folder using `shutil.move` via `/api/move`.
  - Group Drag: Reorders the sequential numbering scheme of the root folders (e.g., swapping `Group2` and `Group3`) via `/api/save-order`.
- UI/UX behavior: 
  - Drag handles (`cursor: grab`) are explicitly required to initiate dragging (prevents accidental drags while selecting text).
  - Valid drop targets highlight dynamically.
  - Global Trash Zone animates into view only when a drag operation begins.
- Edge Cases: Dragging an agent into its own current group is a no-op.
- Acceptance Criteria:
  1. The backend performs the move atomically without duplicating the file.
  2. The UI instantly reflects the new hierarchy.

### 9. Real-Time Disk Mirroring (Watchdog Observer)
- Purpose: Ensure the UI perfectly mirrors the physical file system in real-time without requiring manual browser refreshes.
- Main behavior: A Python `watchdog` process monitors the root `AI Agent Prompts` directory.
- System behavior:

  - Detected changes (file creation, modification, deletion by third-party apps like VSCode or File Explorer) trigger an atomic `migrate_folders_locked()` re-indexing.
  - The UI polls `/api/get-tree` and injects the updated JSON state into the DOM layer automatically.
- Acceptance Criteria:
  1. Creating a folder directly in Windows Explorer instantly spawns a new Group in the browser.

### 10. Agent Bulk Deletion Mode

### 11. Prompt Version History & Safe Restoration
- Purpose: Provide a seamless roll-back plan for edited prompts and handle restore collisions safely.
- Main behavior: 
  - Editing an existing prompt sends the original version to the `[RECYCLE BIN]` with a timestamp before saving the new version.
  - Restoring a file that shares a name with an existing active prompt triggers a "Collision Modal" offering Overwrite or Rename actions.
  - Overwriting an active prompt will automatically recycle the active prompt before completing the restore.
- System behavior: 
  - `bridge.py` utilizes the `move_to_recycle_bin` helper during edit operations.
  - The `/api/recycle-restore` endpoint returns a `409 Conflict` if the destination path already exists, passing `collision=True`.
- Acceptance Criteria:
  1. Old versions of edited prompts are safely retained in the Recycle Bin for 30 days.
  2. The system never blindly overwrites during a restore without explicit user confirmation.

### 14. Visual Copy Timestamp & Auto-Reset
- Purpose: Provide immediate visual indicator of when a prompt was last copied to the clipboard across both the dashboard and editor screens, while ensuring stale copy dates disappear once content changes.
- Main behavior:
  - Clicking either the dashboard card's quick-copy icon or the main "COPY PROMPT" button triggers an atomic `/api/record-copy` request to the backend.
  - The backend writes a lightweight `copy_time.txt` timestamp file inside the target agent folder and broadcasts a sync event via the Watchdog observer.
  - The sync a copy triggers does NOT rebuild the dashboard. `copy_times` are
    excluded from the render fingerprint (buildRenderSignature) and
    `syncCardTimestamps()` patches the `.card-timestamp` spans in place,
    because a full rebuild re-measures and re-packs every group - one copy
    used to scatter the whole board. copyToClipboard() also patches the single
    copied card optimistically, so no rebuild ever runs on the copy path.
- UI/UX behavior:
  - Dashboard cards and editor header display a subtle timestamp strictly formatted as `DD/MM HH:MM` directly beneath the agent title or in the navigation bar without any additional prefix text.
  - The prompt view header displays the timestamp cleanly aligned on the right side of the top navigation bar.
  - A small Reset Counters button positioned immediately to the left of the recycle bin down-arrow button allows users to globally reset and purge all copy timestamps across all prompts at once via `/api/reset-copy-times`.
  - Editing and saving a prompt's text or renaming its title automatically purges the `copy_time.txt` file and resets the timestamp display.
- Acceptance Criteria:
  1. Copying via quick-copy button or main copy button immediately updates the UI with a date/time stamp.
  2. Modifying and saving either the prompt text or title removes the timestamp.
  3. Clicking the Reset Counters button next to the recycle bin prompts confirmation and purges all copy timestamps across the library.

### 15. Dev Automated Git Sync (Push & Force Pull Overlay)
- Purpose: Provide developers with a zero-friction, one-click Git sync and cloud recovery pipeline. Includes automated change detection, smart commit messages, pre-push rebase synchronization, and pushing to remote, as well as a safe force-pull pipeline to overwrite local files with cloud commits when necessary, backed by real-time terminal diagnostics and confirmation safeguards.
- Main behavior:
  - Discreet developer action buttons (`PUSH` and `PULL`) sit directly above the `#bridge-status` pill in the bottom-right corner (`.dev-actions-bar`).
  - **Git Push**: Calls `POST /api/git-push`. Verifies/inits Git, checks user config, derives branch and remote, automatically synthesizes a concise commit summary comparing local files to `origin/<branch>`, stages (`git add .`), commits, runs `git pull --rebase` to incorporate remote changes, and pushes to remote (`git push origin <branch>`).
  - **Git Force Pull**: Clicking `PULL` first triggers a high-visibility warning confirmation dialog detailing that all local changes will be replaced. Upon confirmation, calls `POST /api/git-pull`. Runs `git fetch <remote> <branch>`, `git reset --hard <remote>/<branch>`, and `git clean -fd`, then triggers backend folder re-indexing (`migrate_folders_locked()`) and client-side UI sync (`syncFromBridge()`).
  - Both operations stream command execution and stdout/stderr output in real time over Server-Sent Events (SSE) into `#git-push-terminal`.
- UI/UX behavior:
  - Both buttons render at low resting opacity (0.28) to avoid cluttering normal usage.
  - `PUSH` glows white/blue on hover.
  - `PULL` glows with a distinct, prominent reddish warning tone (`#ff7b72` text, red border, and reddish ambient shadow) on hover to provide an immediate visual risk cue.
  - When clicking `PULL`, an easy-to-understand confirmation modal (`#git-pull-confirm-overlay`) warns the user about pending destructive overwrites with actionable bullet points and requires explicit confirmation (`FORCE PULL & OVERWRITE`).
  - The live terminal console displays colored log streams (`cmd`, `out`, `info`, `warning`, `error`, `success`).
  - On failure, a structured error card explains what happened and why it failed with a `RETRY` button.
  - On success, the modal displays green status indicators and triggers a fading green toast notification (`showToast(..., 'success')`).
- Logic Details:
  - Dynamic Commit Synthesis: Evaluates `git diff --cached --name-status` against `origin/<branch>` (or HEAD) and synthesizes human-readable category summaries: core infrastructure (`bridge.py`, installers), frontend layout/styling (`AI Agent Prompts.html`), architectural documentation (`project_structure.txt`, `README.md`, `CLAUDE.md`), and prompt data additions/modifications.
  - Pre-Push Auto-Rebase: To prevent `[rejected] (fetch first)` non-fast-forward push failures when remote commits exist upstream, the backend runs `git pull --rebase <remote> <branch>`. If conflicts arise, it automatically executes `git rebase --abort` to protect local files and surfaces actionable conflict diagnostics.
  - Safe Force-Pull Protocol: Runs `git fetch <remote> <branch>`, `git reset --hard <remote>/<branch>`, and `git clean -fd`, then invokes `migrate_folders_locked()` to update backend folder state and triggers frontend `syncFromBridge()` to refresh the dashboard DOM.
  - SSE Protocol: Subprocess output lines are streamed in real time using `text/event-stream` with payload format `{"type": "cmd"|"out"|"err"|"info"|"success"|"error"|"done", "text": "..."}`.
- Failure handling:
  - Subprocess errors halt execution and stream detailed diagnostic reasons (stage, what happened, why it failed).
  - Concurrency is protected by a unified `git_op_lock` on the backend and client-side button disablement.
  - Rebase conflicts auto-abort (`git rebase --abort`) immediately to avoid corrupting the working tree.
- Acceptance Criteria:
  1. Discreet 'PUSH' and 'PULL' buttons are positioned side-by-side above the bridge status pill.
  2. 'PULL' button turns reddish on hover as a visual warning cue.
  3. Clicking 'PULL' opens a clear, easy-to-understand destructive action warning dialog.
  4. Confirming force-pull overwrites all local files with cloud commits and cleans untracked files.
  5. Real-time CMD terminal modal streams execution logs live for both push and pull.
  6. Auto-rebase integrates remote changes cleanly before pushing, or cleanly aborts on merge conflicts.
  7. Clear, detailed error breakdowns are presented if any operation fails.
  8. Clear green fading toast appears on successful execution.

8. CACHING POLICY
===============================================================================
- STRICT NO-CACHE POLICY: Both the frontend and backend are explicitly configured
  to prevent caching of any kind.
- Frontend: HTML meta tags and Javascript fetch requests enforce `cache: 'no-store'`.
- Backend: Flask implements an `@app.after_request` hook to inject
  `Cache-Control: no-store, no-cache, must-revalidate, max-age=0` headers on all responses.
- Python Bytecode: No `__pycache__`/.pyc files are ever written. Four layers:
    1. bridge.py sets `sys.dont_write_bytecode = True` as its first statement.
       This covers every module bridge.py IMPORTS.
    2. It cannot cover bridge.py ITSELF. CPython compiles and writes
       __pycache__/bridge.cpython-XXX.pyc BEFORE executing line 1, so an
       `import bridge` from a test harness, a REPL or an AI agent always
       produced a .pyc no matter what line 2 said.
       bridge.py therefore self-heals: `purge_bytecode_cache()` deletes the
       cache at import time and again inside `graceful_shutdown()`.
       *** That block must stay ABOVE every other import. *** A third-party
       import failing higher up (flask not installed) aborts the module before
       the cleanup would otherwise run, leaving the .pyc behind.
       Removals are reported in bridge.log ("No-cache policy: removed ...").
    3. The installer sets `PYTHONDONTWRITEBYTECODE=1` and passes `-B` to every
       Python invocation; its syntax probe uses `ast.parse`, never
       `py_compile`, which would write cache files.
    4. Install.bat and UnInstall.bat delete any stray `__pycache__` folder.

===============================================================================
9. PROMPT EDITOR (EDIT MODE)
===============================================================================
A. Unsaved-Work Protection
   - getEditorText() (box.textContent) is the ONLY way the app reads the editor.
     Save, copy, dirty-check, undo history and the line gutter all use it, so the
     app can never disagree with itself about whether something changed.
   - hasUnsavedPromptChanges() / hasUnsavedTitleChanges() / hasUnsavedWork()
     compare against editBaseContent (the text as of entering edit mode).
   - Escape and the CANCEL button both route through cancelEdit(), which asks for
     confirmation before discarding. Escape also stops propagation so a single
     keypress cannot both exit edit mode and leave the prompt view.
   - A beforeunload handler makes the browser warn before a tab close or refresh
     that would drop unsaved edits.

B. Keyboard Shortcuts (prompt view)
   - Ctrl+S ............ Save changes (suppresses the browser "Save page as" box)
   - Ctrl+Enter ........ Save changes
   - Ctrl+Z / Ctrl+Y ... Undo / Redo (caret preserving)
   - Ctrl+F / Ctrl+H ... Find / Replace       F3 - Find next
   - Ctrl+G ............ Go To Line (styled modal, never window.prompt)
                         NOTE: Ctrl+W is deliberately NOT bound. Browsers reserve
                         it to close the tab and ignore preventDefault().
   - Escape ............ Close search, else cancel edit (with confirmation)

C. Undo / Redo
   - History is a stack of { text } snapshots, capped by BOTH step count
     (EDITOR_HISTORY_LIMIT) and total characters (EDITOR_HISTORY_CHAR_BUDGET),
     so large prompts cannot pin unbounded memory.
   - caretForTextSwap() derives the caret from the first differing character plus
     any re-inserted length, so undo/redo returns the cursor to the edit site
     instead of the end of the document.

D. Line Number Gutter
   - The gutter is sized by its own rows (align-self: flex-start + min-height:100%),
     never stretched. A stretched flex item inside a scrolling container only
     receives the VISIBLE height, which made the divider stop mid-page on long
     prompts. No JavaScript sets the gutter height.
   - updateLineNumbers() diffs the new line array against the previous one and
     re-measures only the changed middle section (common head/tail reuse), and
     skips layout entirely for lines too short to wrap (monospace char-width
     fast path). Rows are reused rather than rebuilt. A normal keystroke
     therefore measures one line, not the whole document.
   - gutterCache is invalidated on stopEdit(); a ResizeObserver on
     #prompt-box-wrap re-syncs numbers after resize, zoom or density changes.

10. GROUP FIT ENGINE (BOARD LAYOUT)
===============================================================================
The board (#main-menu) is a wrapping flex row. The fit engine reproduces the
browser's greedy wrap in JavaScript so the UI can answer layout questions
BEFORE the user releases the mouse.

A. Core (pure, unit-tested)
   - simulateRows(widths, W, gap) -> rows of indices. Mirrors flex-wrap exactly.
   - predictLayout(...) -> {rows, rects}: where every group would sit, in board
     coordinates. Group height does not depend on width (agent cards are a
     single column), so predicted rects are exact.
   - computeSnapTargets(index, metrics, minWidth): scans every candidate width
     once and keeps the WIDEST width producing each distinct row grouping.
     Scanning is used instead of a closed-form formula so the snap points can
     never disagree with simulateRows.

B. Resize Interaction (.custom-resize-handle)
   - Pointer events (works with mouse, pen and touch); pointer capture is used.
   - Grip art: the universal three-diagonal-line gripper, drawn as a 135deg
     repeating-linear-gradient clipped to the lower-right triangle. The stop
     offsets (0.4 -> 1.9 repeating every 3.4px on a 14x14 box) are derived, not
     guessed: they are the only values that place three FULL lines inside the
     revealed half of the gradient axis. Changing the box size or the period
     without redoing that arithmetic yields two lines and two slivers.
     Colour is driven by --grip-color so hover and .is-resizing can recolour it.
     The cursor stays ew-resize because only width is adjustable.
   - Two kinds of snap target, merged into one list; the NEAREST target wins:
       * fit targets   (green)  - a width where a neighbour joins the row, or in
                                  SNUG a width that makes the whole board shorter
       * align targets (violet) - a width identical to another group's width;
                                  the matched group is outlined and #snap-vguide
                                  drops a dashed column line at the shared edge
   - Magnetic snapping within SNAP_TOLERANCE (16px) of a snap target.
     Hold ALT while dragging to bypass snapping for a pixel-exact width.
   - #snap-rail renders a tick per snap target under the group, labelled with
     the group that would join the row. Colliding labels are hidden.
   - #fit-ghost renders a dashed outline at the predicted landing position:
     the incoming group, or (class .self) the dragged group when it is the one
     jumping up a row.
   - DOUBLE-CLICK the handle to shrink-wrap: clears custom_width, restores
     automatic sizing, and POSTs width: null. This is the only way back to auto
     sizing once a width has been set.
   - isResizingGroup suppresses renderMenu() so an external file change cannot
     rebuild the board out from under the cursor mid-drag.

C. TIDY Button (#tidy-btn) - reversible
   - Always packs for MINIMUM BOARD HEIGHT via computeSnugWidths(): it tries
     1..6 uniform column widths, packs each with packMasonry() and keeps the
     shortest board. No group is ever shrunk below its natural width. Heights
     are measured in the same natural-width pass so the packer is never fed
     heights belonging to a different width.
   - Measures every group at its natural width in one pass, packs, justifies,
     applies immediately, then persists.
   - Refuses to run while a search filter is active (the board is partial).
   - Before packing it stores `tidySnapshot`: every group's width exactly as it
     was, with `null` meaning "had no custom width at all". Restoring null puts
     the group back to AUTO sizing rather than freezing it at the pixel value it
     happened to occupy - this is the part that makes the undo lossless.
   - The button then flips to UNDO TIDY (`.undo-state`, gold, undo icon) and
     `onTidyButton()` routes to `undoTidy()` instead. Undo rewrites the DOM,
     the in-memory `groups` state and the backend (nulls clear the width), then
     disarms the button.
   - `clearTidySnapshot()` disarms it the moment the board stops matching what
     TIDY produced: any manual resize drag, or a shrink-wrap double-click. A
     stale undo is never offered.
   - Groups deleted between TIDY and UNDO are skipped, not fatal.
   - Persistence prefers POST /api/save-group-widths (one write pass, ONE SSE
     broadcast). If that endpoint is missing because the bridge has not been
     restarted, it falls back to one /api/save-group-width call per group, so
     TIDY works either way.

E. Board Packing and Per-Group Pinning
   There is NO layout mode switch. The board ALWAYS packs upward; a group that
   should sit on a plain straight row is pinned individually instead, because
   that is a property of the group and not of the whole board.
   - packMasonry() positions every group absolutely so a short group can rise
     into a gap left anywhere above it - maximum density, chosen deliberately
     over order-preserving packing.
       * CONSEQUENCE: screen position never tracks the running order. Order
         badges (.group-order-badge) therefore appear on every group while a
         reorder drag is in progress.
   - THE ARROW (.group-pin-btn), bottom-left of each group:
       * UP arrow, shown whenever there is room directly above: moves that ONE
         group straight up in its OWN COLUMN until it touches something, and
         stores the result as a hand placement. Its `left` never changes and
         nothing else on the board moves. highestFreeTop() does the work.
       * WHY IT WORKS THIS WAY: the arrow used to hand the group back to the
         automatic packer, which picks the lowest-then-leftmost free slot on the
         WHOLE board. For a group on the second row that was usually the gap at
         the top right, so pressing "up" flung it sideways across the screen
         instead of snugging it up where it stood.
       * DOWN arrow, shown when there is no room above but the group is being
         held: releases it, clearing both the hand placement and any row pin so
         it packs automatically again.
       * The button is hidden entirely when neither action would do anything.
   - LEGACY ROW PIN (groups[folder].pin_row):
       * A pinned group is parked at the rect plain row-wrapping would give it.
         That line is computed by predictLayout() over EVERY group, pinned or
         not, so it does not drift as neighbours grow or shrink.
       * Pinned rects are handed to packMasonry() as `fixed` and placed FIRST as
         obstacles; everything else flows around them. packAsRows() returns null
         when the fixed rects do not match the row layout, so that strategy is
         skipped rather than silently violating a pin.
       * The arrow points DOWN (push onto the row line) when free and UP
         (release) when pinned. .can-pin only shows the button when pinning
         would actually move the group, so it is never a control that visibly
         does nothing. .is-pinned draws a gold underline so the state is
         readable without hovering.
       * Persisted as "pin_row" in <group>/group_meta.json via
         POST /api/save-group-pin. If that endpoint is missing because the
         bridge has not been restarted, the frontend keeps the choice in
         localStorage('pinRow:<folder>') so the feature still works.
       * packMasonry runs THREE strategies (bottom-left fill, bottom-left fill
         with left-edge alignment, and plain rows) and keeps the shortest board.
         Greedy bottom-left alone is myopic - it wedges a wide flat group into a
         low pocket and blocks the shelf a later group needed, occasionally
         producing a TALLER board than rows. The three-way search makes SNUG
         mathematically incapable of losing to ROWS; a 2000-board fuzz test
         verifies zero overlaps, zero off-board boxes and zero regressions.
   - applyBoardLayout() measures with the board temporarily back in ROWS layout.
     An absolutely positioned box with width:fit-content shrinks to the space
     left of its containing-block edge, so a group parked at x=600 would measure
     narrower than it is. Measure-in-flex then re-apply happens inside ONE
     synchronous block, so the browser never paints the intermediate state.
     Widths are then pinned in px (dataset.snugPin marks a pin as presentation
     only - it is never written back to custom_width).
   - The measure pass runs under #main-menu.measuring, which forces
     content-visibility:visible on .agent-card. content-visibility:auto makes
     never-painted off-screen cards answer with their contain-intrinsic-size
     estimate instead of their real height, so a rebuild packed guessed sizes
     and the board drifted a little differently every time. The class is added
     and removed inside the same synchronous block as the snug-mode toggle,
     so nothing is ever painted with it.
   - The board is re-packed after a render, after shrink-wrap, after
     TIDY/RESET/UNDO/pin, at the end of a group drag, and whenever the board's
     own width changes (ResizeObserver, guarded against feedback).
   - FREE PLACEMENT. A group can be dropped anywhere there is room, including a
     half-empty bottom row or a slot that is not the next one along. The board
     is no longer a single left-to-right sequence.
       * A dropped group becomes an ANCHOR: it keeps exactly the spot it was
         given (fed to packMasonry as a `fixed` rect) and every group that has
         NOT been placed by hand flows around it.
       * DRAGGING NO LONGER RENAMES FOLDERS. A drop records a position and
         nothing else - no backend call at all. The folder-renaming path, which
         once made three groups vanish and which Windows regularly denies, is
         off the drag path entirely. Ctrl+Left / Ctrl+Right on a group's drag
         handle remains the way to change the real list order, and it builds its
         list from Object.keys(groups) so it can never be partial.
       * Placements live in localStorage under `boardPlacement:<width>`, bucketed
         to PLACEMENT_WIDTH_BUCKET (20px). Return to the same window size and the
         arrangement comes back; change size and it is ignored, because an
         arrangement built for 1900px says nothing about 1200px. Nothing is ever
         written to the prompt folders, so rearranging cannot touch user data.
       * A drop snaps to neighbouring edges within PLACEMENT_SNAP (12px) and is
         clamped inside the board and to one gap below the lowest box, so a
         group cannot be lost off-screen or stretch the board into the distance.
       * Dropping onto an already-placed group PUSHES it aside
         (pushOverlappingPlacements): it slides straight down to the nearest
         free spot and STAYS hand-placed, keeping its column. Releasing it used
         to throw away the position the user had chosen and let the packer fling
         it elsewhere. Each move is returned as {folder, from, to}, which is what
         makes the whole drop undoable.
       * resolveFixedRects() settles the hand-placed rectangles against EACH
         OTHER before anything is packed around them. Without it, widening one
         placed group into another simply stacked them and one vanished behind
         the other - fixed rects were never compared with each other at all.
         The `fixedOrder` argument gives the group under the cursor priority, so
         the one being dragged is never the one shoved aside.
       * snapPlacement() measures every candidate from the ORIGINAL drop point.
         It used to compare each candidate against a value it had already
         modified, so the reference drifted and the same drop gave different
         answers depending on the order the groups happened to be in. The board's
         own left, right and top edges are candidates too, so a group can be sat
         flush in a corner.
       * Snap references are FROZEN when the drag starts (captureSnapRefs). The
         board re-packs every frame, so snapping against live positions meant
         aiming at a target that moved as you approached it.
       * #place-vguide / #place-hguide draw smart guides whenever the drop rect
         snaps, so "line this up with that" is visible rather than guessed.
       * Every drop offers a single UNDO (showUndoToast) restoring both the
         dropped group and everything it pushed aside. Previously the only way
         back was RESET LAYOUT, which wipes the entire board.
       * Storage is pruned: readPlacements() drops folders that no longer exist,
         and writePlacements() keeps only the PLACEMENT_MAX_BUCKETS most recent
         window widths. Both used to grow for ever.
       * The old row-pin concept is GONE. migrateLegacyPins() converts any
         surviving pin into an ordinary placement once, then the flag is deleted
         from state, from localStorage and from group_meta.json. /api/save-group-pin
         has been removed. Two competing notions of "held in place" was one too
         many.
       * applyBoardLayout() caches the measured sizes for the duration of a drag
         (beginDragSizeCache / endDragSizeCache) and re-measures only the element
         under the cursor, whose width really can change. A drag used to force
         two full layout reflows every animation frame to learn nothing new.
       * RESET LAYOUT clears every placement for the current width as well as the
         widths, and the shared UNDO restores both.
   - REORDER DRAG (what-you-see-is-what-you-get):
       * .group-placeholder is packed as if it WERE the dragged group, and the
         dragged group itself is hidden (.group-dragging) and excluded. The
         dashed box therefore sits exactly where the group will land, and every
         other group is already in its final position before the drop.
       * EVERY element the board lays out must be box-sizing: border-box in its
         BASE rule. applyBoardLayout() measures the border-box width and writes
         it back as the width; on a content-box element that re-adds the border
         each repack, growing the box ~4px per animation frame during a drag.
         Declaring it only inside .snug-mode does not work, because measuring
         happens with that class temporarily removed. The anchor element is also
         skipped by the width-rewrite entirely, as a second line of defence.
       * The placeholder must be absolutely positioned in the packed board and
         have its 150px flow minimum cancelled. Left in the document flow it
         rendered as one giant dashed box across the whole board, and moving it
         previewed nothing at all, because the other groups take their positions
         from the packer rather than from the flow.
       * A move re-packs with the placeholder pinned at the cursor
         (computeDropRect), the same rect the drop will store, so preview and
         result cannot disagree. It no longer shuffles the list or renumbers,
         because dragging cannot change the order any more.
       * flip() is not used for group dragging. It animates transforms while the
         board drives left/top, so the two fought each other. flip() is still
         correct for agent cards inside a group, which are genuinely
         flow-laid-out.
       * The drop re-packs BEFORE animateGhostTo(), otherwise the ghost flies to
         the position the group started from and the board then jumps elsewhere.
       * The board also re-packs on pick-up so the hole closes immediately.
   - DURING a resize drag it also repacks live, with the dragged group handed to
     packMasonry() as a fixed rect at its current position.
     TWO ORDERING RULES make this safe, and breaking either one silently throws
     the user's resize away:
       1. The measure pass restores every group's width from custom_width. It
          MUST skip the anchored group - custom_width still holds the OLD value
          until the drag ends, so restoring it mid-drag undoes the resize on
          every single frame and the group snaps straight back.
       2. onUp must READ and COMMIT the final width BEFORE calling
          applyBoardLayout(). Packing first restores the old width, so the
          measurement comes back equal to custom_width and the save is skipped
          entirely - the resize is discarded without a word. .no-anim is held on
     the board for the whole drag so neighbours track the cursor instantly
     instead of lagging behind a 0.28s transition. Holding it still is
     what stops the box sliding out from under the cursor while its neighbours
     reflow around the new width. The repack is coalesced to at most one per
     animation frame. The old #fit-ghost landing preview was retired: with the
     whole board reflowing live, a single predicted rectangle contradicted what
     was already on screen.

F. RESET LAYOUT (#reset-layout-btn)
   - Confirms first, then clears custom_width on every group so each returns to
     sizing itself. Group ORDER is never touched - width and order are
     independent and the backend owns ordering.
   - Refuses to run while a search filter is active (the board is partial).
   - Reuses tidySnapshot, so the shared UNDO button restores it; the button
     reads UNDO RESET rather than UNDO TIDY (tidySnapshot.source).

G. Backend
   - POST /api/save-group-width   {group, width|null}   - single group
   - POST /api/save-group-widths  {widths: {folder: width|null}} - batch
     Both write custom_width into <group>/group_meta.json. A null width pops
     the key. The batch route validates each folder through safe_path(), caps
     the request at 500 groups and clamps widths to 1..20000.
   - POST /api/git-push           {}
     Automated developer sync pipeline. Stages all changes (git add .),
     synthesizes a concise commit summary comparing against online remote,
     creates commit, integrates upstream commits via 'git pull --rebase'
     (auto-aborts via 'git rebase --abort' on conflict), and pushes to remote
     (git push origin <branch>) while streaming real-time stdout/stderr lines
     over Server-Sent Events (SSE). Protected by git_op_lock.
   - POST /api/git-pull           {}
     Automated developer force-pull pipeline. Fetches cloud commits, resets
     local working tree and index (--hard), cleans untracked files (-fd)
     to match the cloud repository, triggers backend folder re-indexing
     (migrate_folders_locked()), and signals client sync (syncFromBridge())
     while streaming real-time stdout/stderr output over SSE.
